## 3. What is broken (the single live blocker)

### Symptom

The `splitter` container is in a **restart loop** — `Restarting (1) 34
seconds ago`, has been cycling for 36+ minutes. Every restart prints the
same sequence and FATALs at the same line:

```
[entrypoint] NVIDIA devices visible
[entrypoint] libgstnvcodec.so found at /usr/lib/x86_64-linux-gnu/gstreamer-1.0/libgstnvcodec.so
[entrypoint] FATAL: gst-inspect-1.0 nvv4l2decoder failed (plugin not loadable)
[entrypoint]   libgstnvcodec.so is installed at /usr/lib/x86_64-linux-gnu/gstreamer-1.0/libgstnvcodec.so but the
[entrypoint]   element 'nvv4l2decoder' is not registered. Common causes:
[entrypoint]     - The .so failed to load (check 'gst-inspect-1.0 nvcodec')
[entrypoint]     - A symbol dependency is missing (libnvidia-encode,
[entrypoint]       libnvcuvid, libcudart) — should be in cudnn-devel base
```

### What has been ruled out (do not re-investigate)

- ❌ **Not a missing `.so`** — `libgstnvcodec.so` is at the expected path.
- ❌ **Not a link-time problem** — `ldd` resolves all GStreamer deps.
- ❌ **Not a missing `libcuda`/`libnvcuvid`/`libnvidia-encode`** — the
  `535.309.01` series (installed via `cuda-keyring`) and the
  `590.48.01` series (injected by the `nvidia` runtime) are both
  present. Unsuffixed symlinks (`libcuda.so`, `libnvcuvid.so`,
  `libnvidia-encode.so`) all resolve to `.so.1` correctly.
- ❌ **Not a `dlopen` problem on `libcuda`** — a probe inside the
  container with `dlopen("libcuda.so.1", RTLD_NOW)` returns a valid
  handle. `cuInit` and `cuDeviceGetCount` are present at non-NULL
  addresses inside that handle.

### The actual failure

`gst-inspect-1.0 nvcodec` prints the plugin header (`Name: nvcodec`,
`Version: 1.20.3`, `License: LGPL`, …) and then **`0 features:`**. The
.so loads, `plugin_init` runs, but it returns without calling
`gst_element_register` for any of the 9 nvcodec elements
(`nvv4l2decoder`, `nvv4l2h264enc`, `cudaconvert`, etc.).

The most likely root cause (needs the `cuInit` return code to confirm):

GStreamer 1.20.3's `gst-plugins-bad/sys/nvcodec/` `plugin_init` (June
2022, hard-coded for the CUDA 11.x/early-12.x Video SDK ABI) calls
`cuInit(0)` and on non-zero return, or on driver-version < expected,
**silently returns** before registering elements. The host's NVIDIA
driver is `570+` (per `nvidia-smi`) and the runtime-injected userland
libcuda is from the `590.x` series. The plugin may be returning
`CUDA_ERROR_INSUFFICIENT_DRIVER` or `CUDA_ERROR_UNKNOWN` from the
ABI/version check inside `plugin_init`.

### Downstream impact

- `gst-inspect-1.0 nvv4l2decoder` → "no such element" → entrypoint FATAL
  → container exit 1 → docker restart → loop.
- Port 8556 never opens → Frigate's `go2rtc` gets connection refused on
  the 6 new streams → the 6 new cameras stay `disabled` in Frigate.

## 4. The single concrete next step (when work resumes)

**Run a one-shot CUDA probe inside the image to capture the
`cuInit(0)` return code and the reported driver version.** This will
distinguish between the 4 root-cause candidates below and pick the right
fix.

### Command to run

```bash
docker run --rm --runtime=nvidia --gpus all --network host \
  --entrypoint sh frigate-splitter:local -c '
    set -e
    which gcc >/dev/null 2>&1 || (apt-get update && apt-get install -y --no-install-recommends gcc)
    cat >/tmp/cuda_probe.c <<EOF
#include <stdio.h>
#include <cuda.h>
int main() {
  CUresult r;
  int n=0, driver=0;
  r = cuInit(0);
  printf("cuInit(0) = %d (%s)\n", r, cudaGetErrorName(r));
  if (r != CUDA_SUCCESS) return 1;
  cuDriverGetVersion(&driver);
  printf("driver version: %d (=%d.%d)\n", driver, driver/1000, (driver%100)/10);
  cuDeviceGetCount(&n);
  printf("device count: %d\n", n);
  if (n < 1) return 0;
  CUdevice d=0; cuDeviceGet(&d, 0);
  char name[256]={0}; cuDeviceGetName(name, 255, d);
  int cc=0; cuDeviceGetAttribute(&cc, CU_DEVICE_ATTRIBUTE_COMPUTE_CAPABILITY, d);
  printf("device 0: %s (cc=%d.%d)\n", name, cc/10, cc%10);
  return 0;
}
EOF
    gcc /tmp/cuda_probe.c -o /tmp/cuda_probe -lcuda && /tmp/cuda_probe
'
```

### Decision matrix from the probe output

| `cuInit(0)` | `cuDeviceGetCount` | Driver version | Most likely cause | Go to fix |
|---|---|---|---|---|
| `0` (SUCCESS) | `0` | any | `nvidia` runtime injection broken by `network_mode: host` + `deploy.resources` | **C** |
| `0` (SUCCESS) | `>=1` | 535.x–545.x | nvcodec `plugin_init` ABI check is the real culprit, not `cuInit` | **D** |
| `0` (SUCCESS) | `>=1` | 570+ | Same as above; nvcodec 1.20.3 cannot talk to driver 570+ | **D** |
| `100` (INSUFFICIENT_DRIVER) | n/a | n/a | nvcodec 1.20.3 was built against a newer CUDA Video SDK than the host's driver supports | **D** or **E** |
| `999` (UNKNOWN) or `700` (ILLEGAL_STATE) | n/a | n/a | runtime injection partially failed; libs load but handshake broke | **C** then **B** |


```sh
# Before the loop, also check the parent plugin:
```

### Fix B — drop `cuda-keyring` libs entirely; let the nvidia runtime inject

If the probe shows `cuInit = 0` but `cuDeviceGetCount = 0` (runtime
injection broken), the simplest fix is to **not install the
`libnvidia-compute-535` / `libnvidia-encode-535` / `libnvidia-decode-535`
packages at all** in the Dockerfile. The `nvidia` container runtime
already mounts the host's libs at the same paths; installing the
userland 535 series alongside the 590 series injected by the runtime
causes the unsuffixed symlink to flip between versions depending on
which package was installed last, breaking `dlopen` for the nvcodec
plugin.

In [`splitter/Dockerfile:141`](Dockerfile:141) replace the entire
`libnvidia-*` install block with:

```dockerfile
RUN set -eux; \
    # The NVIDIA driver userspace libs (libcuda.so, libnvcuvid.so,
    # libnvidia-encode.so) are NOT installed in this image — they are
    # provided at container start by the nvidia container runtime,
    # which bind-mounts the host's driver libraries over the canonical
    # paths in /usr/lib/x86_64-linux-gnu/. The previous build installed
    # 535-series userland libs via the cuda-keyring, which fought the
    # 590-series host libs the runtime injects. See HANDOFF-2026-06-03.md
    # for the full diagnosis.
    apt-get update && apt-get install -y --no-install-recommends \
        software-properties-common wget gnupg ca-certificates \
    && rm -rf /var/lib/apt/lists/* && \
    git clone --depth 1 --branch 1.20.3 \
        https://gitlab.freedesktop.org/gstreamer/gstreamer.git /tmp/gst && \
    ...
```

After the change, **rebuild the image** with `docker build -t
frigate-splitter:local .` from `splitter/`, then `docker compose -f
splitter/docker-compose.splitter.yml up -d`. The build will still
succeed because the `cudnn-devel` base image has the `libnvidia-encode`
and `libnvcuvid` headers needed at link time (those are separate from
the runtime libs).

### Fix C — switch from `network_mode: host` to bridge + host port mapping

If Fix B doesn't work, the next suspect is that `network_mode: host` in
[`splitter/docker-compose.splitter.yml:35`](docker-compose.splitter.yml:35)
interferes with the `nvidia` runtime's library injection (the runtime
hooks into the container's mount namespace; `network_mode: host`
changes that namespace layout). Switch to bridge networking with an
explicit port mapping:

```yaml
# In splitter/docker-compose.splitter.yml
    ports:
      - "8556:8556/tcp"   # gst-rtsp-server; Frigate's go2rtc is on 127.0.0.1:8554 in the frigate container, so this port is only reachable from the host
    # REMOVE: network_mode: host
```

Note: this requires the Reolink cameras to be reachable from the bridge
network. Since they're at `192.168.50.7/18/129` on the LAN, docker's
default bridge + the host's default route will reach them. Verify with
`docker exec splitter ping -c1 192.168.50.129` after the change.

### Fix D — bump to a newer GStreamer

If the probe shows `cuInit = CUDA_ERROR_INSUFFICIENT_DRIVER` (700) or a
driver version > 545, the source-built GStreamer 1.20.3 cannot talk to
the host's driver. Two sub-options:

- **D1** (light): edit [`splitter/Dockerfile:155`](Dockerfile:155) to
  clone a newer GStreamer branch (`1.24` is current LTS), and update the
  element name `cudaconvert` (which is what 1.20 uses) to match
  whatever the newer version expects (1.24 still uses `cudaconvert`,
  but verify with `gst-inspect-1.0 cudaconvert` in the rebuilt image).

  ```diff
  -    git clone --depth 1 --branch 1.20.3 \
  -        https://gitlab.freedesktop.org/gstreamer/gstreamer.git /tmp/gst && \
  +    git clone --depth 1 --branch 1.24.10 \
  +        https://gitlab.freedesktop.org/gstreamer/gstreamer.git /tmp/gst && \
  ```

- **D2** (medium): drop the source build entirely and install
  `gstreamer1.0-plugins-bad` from the system repos (Ubuntu 22.04 ships
  1.20.3 — the version we already have, so this is a no-op) **or** add
  the GStreamer PPA (`ppa:gstreamer-developers/ppa`) for 1.24.x.

  **NOT recommended**: the PPA approach is what we explicitly rejected
  at the start of this branch (commit `60739f7` rationale). The
  source-build is more reproducible.

### Fix E — fall back to the DeepStream base image

If B/C/D all fail, switch to option A from
[`splitter/Dockerfile:14`](Dockerfile:14): the DeepStream 7.0 NGC image
ships a known-working pre-built `libgstnvcodec.so`. Trade-offs:

- ✅ Pre-built, pre-tested, less code to maintain.
- ❌ Requires `docker login nvcr.io` (free NGC account, one-time).
- ❌ ~15 GB on disk (vs 9.58 GB today).
- ❌ Has DeepStream SDK + Triton inference server pre-installed that we
  don't need (dead weight but harmless).
- ❌ Slower pull on first build.

Procedure:

1. `docker login nvcr.io` (one-time, free account at
   `https://ngc.nvidia.com/signup`).
2. Edit [`splitter/Dockerfile:59`](Dockerfile:59) to:
   ```dockerfile
   FROM nvcr.io/nvidia/deepstream:7.0-triton-multiarch
   ```
3. Delete the entire `RUN` block at
   [`splitter/Dockerfile:141-174`](Dockerfile:141) that builds
   `gst-plugins-bad` from source (the plugins are already in the
   DeepStream image at
   `/opt/nvidia/deepstream/deepstream/lib/gst-plugins/`).
4. In [`splitter/entrypoint.sh`](entrypoint.sh) add to `GST_PLUGIN_PATH`:
   ```sh
   export GST_PLUGIN_PATH="/opt/nvidia/deepstream/deepstream/lib/gst-plugins:${GST_PLUGIN_PATH:-}"
   ```
5. `cd splitter && docker build -t frigate-splitter:local .` (slower
   first build because of the 5 GB base pull; subsequent builds
   incremental).
6. `docker compose -f splitter/docker-compose.splitter.yml up -d`.

### 6.3 Upgrade the soft-WARN probe in test-config.sh to FAIL

[`tests/test-config.sh:210`](tests/test-config.sh:210) currently does a
TCP connect to 127.0.0.1:8556 and reports `WARN` if it's not
reachable, but does not increment `L1_FAIL`. If the operator has wired
up the 6 new cameras in `config.yml` (which is the documented expected
state per [`STARTUP.md`](STARTUP.md)), a missing splitter is a
**structural** problem, not a soft warning — the cameras will be
`disabled`. Upgrade to FAIL with a clear remediation message:

```bash
# Replace the existing soft-WARN block at tests/test-config.sh:210
if command -v timeout >/dev/null 2>&1; then
    if timeout 2 bash -c '>/dev/tcp/127.0.0.1/8556' 2>/dev/null; then
        printf "  %b[ OK ]%b  splitter RTSP port 8556 is accepting connections\n" "$GRN" "$NC"
        L1_OK=$((L1_OK+1)); L1_TOTAL=$((L1_TOTAL+1))
    else
        printf "  %b[FAIL]%b  splitter RTSP port 8556 is NOT reachable\n" "$RED" "$NC"
        printf "              the 6 new half-cropped cameras (allee_sur_le_cote_left/_right,\n"
        printf "              jardin_devant_left/_right, piscine_vue_toit_left/_right) consume\n"
        printf "              their RTSP streams from the splitter and will be 'disabled'\n"
        printf "              in Frigate until the splitter is up. To start it:\n"
        printf "                cd splitter && docker build -t frigate-splitter:local .\n"
        printf "                docker compose -f splitter/docker-compose.splitter.yml up -d\n"
        L1_FAIL=$((L1_FAIL+1)); L1_TOTAL=$((L1_TOTAL+1))
    fi
fi
```
