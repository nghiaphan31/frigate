# Phase 5: Per-Camera Threshold Re-derivation (2026-07-31)

## Context

Commit [`0b42d46`](../tests/camera_spec.py) (post-iter1) restored the
iter0 physics-derived detection contract on all 5 outdoor Reolink cameras:
`threshold=0.55, min_score=0.45`. Those values were calibrated against
the **old generic SSD model's** score distribution (the +0.10/+0.05
delta from the model default). The new
[`plus://c1aa04320f389aa6c7702bf9ddd3fe6d`](../config.yml) yolonas model
(46 classes, trained 2026-07-30 on 9 camera sub-regions of the 5 outdoor
Reolink streams) may have a different score band on the same geometry.

The iter0 contract is the **safe baseline** to start the soak with. But
once we have 24-48h of person events under the new model, we may be
able to **tighten** the threshold (reject more noise without losing
real detections) or may need to **relax** it (if the new model scores
lower than the old SSD on this geometry).

This document is the procedure for doing that re-derivation
data-driven, with a per-camera decision matrix and a script
([`tests/phase5-derive-thresholds.py`](../tests/phase5-derive-thresholds.py))
that automates the percentile + verdict computation.

## 1. Procedure

### Step 0 — prerequisite: the live Frigate stack must be on the iter0 config

The Phase 4 commit (`0b42d46`) is on the
`post-iter1-custom-model-optimisation` branch in this repo, but the
running Frigate container was last started with the old training
config. You need to:

1. Pull the branch: `git checkout post-iter1-custom-model-optimisation`
   on Calypso (or wherever the config volume is mounted)
2. Restart the stack: `./install-and-restart.sh` (uses sudo; restarts
   `frigate-stack.service` via systemd, picks up the new config.yml)
3. Wait for bring-up: `bash tests/test-bringup.sh` should return
   14/14 OK on the L3 report

### Step 1 — collect a 24-48h soak

You need person events under the iter0 (0.55/0.45) contract to know
what the new model's score band looks like. The training period
(2026-06-04 → 2026-07-30) doesn't count — those events were scored
under the relaxed threshold/min_score and are biased.

A 24h soak gives a few hundred events per camera on busy cameras
(`allee_sur_le_cote`, `jardin_devant`); 48h is safer for the quieter
ones (`piscine_vue_toit`, `jardin_arriere`).

### Step 2 — run the analysis

```bash
make phase5                          # all 5 outdoor cameras, last 10000 events each
make phase5 CAMS=vue_entree          # one camera only
make phase5 JSON=out/phase5.json     # also write raw JSON for diffing
```

The script:
1. Calls `/api/events?cameras=<cam>&labels=person&limit=10000` for each camera,
   paginating with `after=<end_time>` until full
2. Filters to `label == "person"` (the API call already does this, but
   we re-filter as a safety net — audio events with `data.top_score`
   should not contaminate the distribution)
3. Computes p5/p25/p50/p75/p95/min/max
4. Computes the false-positive band rate (top_score in [0.30, 0.55)) —
   this is the band the iter0 contract wants to reject
5. Computes the below-iter0-threshold rate (top_score < 0.55)
6. Applies the decision matrix (§4) to recommend a new
   (threshold, min_score) per camera
7. Prints a per-camera markdown table + per-camera rationale + optional JSON

### Step 3 — review the per-camera table

For each camera, the output is one of 5 verdicts:

| Verdict | Meaning | Action |
|---|---|---|
| `KEEP iter0` | The new model is well-calibrated for this camera | No change |
| `TIGHTEN` | The new model is over-confident (or there's a lot of noise in the low-confidence band) | Bump threshold/min_score up |
| `RELAX` | The new model is under-confident (or the iter0 contract is rejecting too much real signal) | Drop threshold/min_score down |
| `INSUFFICIENT DATA` | n < 20 person events for this camera in the window | Wait for more soak |
| `ERROR` | Frigate API error | Check bring-up |

### Step 4 — apply the recommendation (if any)

For each camera that needs a change:

1. Open `tests/camera_spec.py`
2. Update the spec's `expected_threshold` and `expected_min_score` for
   that camera (e.g. `0.55` → `0.60` for a TIGHTEN)
3. Also update the `expected_zones.<zone>.filters.person.threshold` to
   match (the in-zone filter is layered on top of the camera-level
   filter and should be no more permissive than the camera-level)
4. Run `make iter0-revert-y CAM=<name>` — this will surgical-rewrite
   the camera block in `config.yml` to match the new spec
5. Run `make test` — both L1 and L2 should still be 139/139 OK
6. Commit on the same branch (e.g.
   `chore(detection): apply phase5 threshold tuning from <date> soak`)

The commit message should include the per-camera table from the
script output, so the next operator can see what the data-driven
recommendation was based on.

### Step 5 — re-soak

Wait another 24-48h, re-run `make phase5`, and confirm the new
verdicts are `KEEP iter0` (or no worse than they were). If a camera
goes from `TIGHTEN` back to `KEEP iter0`, you've found the right
value. If it goes from `TIGHTEN` to `RELAX`, you've over-tightened
and need to back off.

## 2. When to stop iterating

Stop when:

- All 5 outdoor cameras show `KEEP iter0` (or `KEEP iter0 (borderline)`)
  in the second soak
- The false-positive band rate is < 5% on every camera
- The below-threshold rate is < 15% on every camera (i.e. we're not
  rejecting too many real detections)

If a camera persistently shows `TIGHTEN` after multiple soaks, the
right answer is probably "this camera needs a smaller crop or a
different model" — not "keep tightening the threshold" (which would
eventually suppress all detections).

## 3. When NOT to use this script

- During the training period (relaxed filter bias — script would
  recommend TIGHTEN spuriously)
- Right after a config change (need 24-48h of new events to have a
  representative distribution)
- When n < 20 per camera (the decision matrix needs at least 20
  events to distinguish signal from noise — the script returns
  `INSUFFICIENT DATA` in this case)

## 4. Decision matrix rationale

The matrix is designed to be **conservative**: it only changes
threshold/min_score by 0.05 in either direction, and it only
recommends a change when the data is unambiguous. The thresholds
come from the iter0 spec's documented +0.10/+0.05 delta from the
"model default" (0.45/0.40 for the old SSD) — those deltas are
what the new model would need to deviate from to warrant a change.

### TIGHTEN triggers

```
p5 >= 0.65  AND  fp_band_rate < 0.05  AND  median >= 0.80
```

The new model is consistently over-confident on this geometry. The
p5 ≥ 0.65 condition ensures the LOWEST 5% of events (which the iter0
contract lets through) are still well above the proposed tightened
threshold. The fp_band_rate < 5% condition ensures we're not
introducing new false positives. The median ≥ 0.80 condition
ensures the bulk of the distribution is well above the tightened
cutoff. The recommendation: 0.55 → 0.60, 0.45 → 0.50.

```
fp_band_rate > 0.15
```

The iter0 contract is letting through too many low-confidence
events. The recommendation: 0.55 → 0.60 (we leave min_score at
0.45 because NMS still needs to filter among the high-confidence
detections).

### RELAX triggers

```
p5 < 0.40
```

The new model is consistently under-confident on this geometry
(likely a low-light or far-distance case the yolonas training set
under-represented). The recommendation: 0.55 → 0.45, 0.45 → 0.35.

```
below_threshold_rate > 0.30  AND  p5 >= 0.40
```

Too many valid events are being rejected by iter0 while the long
tail IS real signal. The recommendation: 0.55 → 0.50, 0.45 → 0.40.

### KEEP iter0 trigger

```
p5 >= 0.55  AND  fp_band_rate < 0.05
```

The new model is well-calibrated. The iter0 contract is correct.

### INSUFFICIENT DATA trigger

```
n < 20
```

The decision matrix needs at least 20 events to distinguish signal
from random scoring noise. The script returns
`threshold=0.55, min_score=0.45` (the iter0 default) and asks the
operator to wait for a longer soak.

## 5. Exit codes

| Code | Meaning |
|---|---|
| 0  | All evaluated cameras produced a recommendation (KEEP / TIGHTEN / RELAX / ERROR) |
| 1  | At least one camera was INSUFFICIENT DATA (operator should re-soak) |
| 2  | Prerequisite missing (config.yml not found) |
| 3  | Frigate API unreachable (bring-up the stack first) |
